# Retrospective: run 20261008-144633-e203

Task: Build a new local-first freelance finance tracker phone app with Expo (React Native) for iOS and Android. Privacy is the product: all of the user's data stays on their device. There is no server, no accounts, no sign-up or login, no analytics, tracking or crash reporting, and the app never sends user data anywhere. Must-haves: (1) Policy agreement gate: on first launch, and whenever the policy version changes, the user must read the Terms of Use and Privacy Policy and tick "I agree" before anything else in the app is reachable; acceptance (policy version and date) is stored on the device. The policy says plainly that data stays on the device and the developer never receives it, that the user is responsible for their own backups, and that the app is not tax, legal or financial advice. (2) Receipts: photograph with the camera (photo-library fallback) and record amount, date, category, type (expense by default, or income) and notes; photos are kept in the app's private storage. (3) Mileage log: date, miles and purpose, with the deduction at a configurable rate per mile (default: the current IRS standard business rate, labeled "verify for your tax year"). (4) Dashboard: income, expenses, mileage deduction and estimated tax at a configurable rate (never negative), recent activity, and every primary action one tap away. (5) Exports: tax-ready CSV and PDF generated on the device and shared through the share sheet. (6) Encrypted on-device storage: the database is encrypted at rest with a key kept in the device keychain/keystore (expo-secure-store). (7) Backup and restore: export one encrypted backup file containing all records and photos, protected by a passphrase the user chooses (strong key derivation and authenticated encryption from an audited JavaScript library such as @noble/ciphers and @noble/hashes), shared wherever the user chooses (Files, iCloud Drive, Google Drive); restore from such a file with the passphrase after a clear confirmation, with an integrity check and a friendly message for a wrong passphrase or damaged file. Cloud-provider sync is out of scope for now. (8) Optional app lock with Face ID, Touch ID or fingerprint (expo-local-authentication), OFF by default and switchable in Settings. (9) Settings: app lock, mileage rate, tax rate, backup and restore, view the policy, and delete all data (with confirmation). The app must be visually appealing, polished and very easy to use: React Native Paper (Material 3) with a theme and shared components, generous spacing, a clear visual hierarchy, friendly empty states and a bottom tab bar to every main area. Use the current Expo SDK (look up versions with npm view; never guess). Includes unit and integration tests of the on-device logic.

## Improvements for the next run

1. **[high] Add a Public‑API Export Validator**
   - Evidence: Round 1: "TypeError: (N , _memory.createStore) is not a function" – caused by missing export of createStore. Round 15‑16: "TypeError: (0 , _backup.createBackup) is not a function" – missing export of createBackup/restoreBackup. These errors appeared in 5 separate rounds and blocked both UI flow and TypeScript checks.
   - Change: static validator (validate.py): introduce a new validator that parses all acceptance‑test import statements, extracts required symbols, and checks that each symbol is exported from the referenced module. If any export is missing, emit a clear message: "Missing export X from path Y – add `export { X }` or implement the function".
   - Expected effect: Missing‑export errors will be caught before the coder proceeds, preventing repeated TypeError failures and saving dozens of coder turns per run.
2. **[high] Make UI‑flow Validator Actionable**
   - Evidence: UI primary flow validator blocked 15 of 19 rounds (e.g., round 1 – checkbox state never changes, round 65 – file‑chooser timeout). Reviewer feedback repeatedly pointed at the same UI problems without pinpointing the component code, leading to many revisions.
   - Change: ui_check.mjs (UI validator): enhance it to (a) map each ui_flow step to a selector/React component name, (b) when a step fails, include the selector, expected property (e.g., aria‑checked, onPress), and a short suggestion (e.g., "Add `aria‑checked={checked}` to the Pressable representing the policy checkbox"). Also add a fallback rule for native file pickers: if a step expects a file‑chooser, suggest using `expo-document-picker` on native and a hidden `<input type='file'>` on web.
   - Expected effect: Coder receives concrete UI fixes instead of generic “step failed” messages, reducing repeated UI‑flow failures and cutting down the number of rounds where UI validation is the sole blocker.
3. **[medium] Structure Reviewer Feedback into Machine‑Parseable Diffs**
   - Evidence: Across rounds 7‑19, reviewer messages were free‑form prose (e.g., "src/lib/backup.ts is an empty file", "add missing import for decrypt"), causing the coder to spend many turns locating the file/line and applying the change. The same issues (missing imports, empty files) were re‑reported in multiple rounds (e.g., rounds 15, 16, 17).
   - Change: reviewer prompt: require the reviewer to output a JSON array `[{"file":"src/lib/backup.ts","action":"addExport","code":"export const createBackup = …"}, …]`. The feedback message to the coder after each round will include this array alongside a short natural‑language summary. The coder agent will be instructed to apply these diffs automatically before generating new code.
   - Expected effect: Reduces ambiguity, eliminates repeated manual searching, and shortens the number of turns needed to satisfy a reviewer issue, directly addressing the turn‑limit overruns seen in rounds 1, 8, 15 and 19.
4. **[medium] Require Explicit Public‑API & Component Map in DESIGN.md**
   - Evidence: Missing milestone 4 files (backup/restore) and missing UI components (ExportScreen, BackupScreen) were only discovered after multiple coder rounds (see rounds 7‑11). The UI flow spec referenced components that did not yet exist, causing the validator to fail continuously.
   - Change: planner prompt: add a clause that the designer must produce a "Component & API Specification" section in DESIGN.md listing every required screen/component, exported function, and its signature (e.g., `createBackup(store: Store, passphrase: string): Promise<Blob>`). After design, a pre‑coder validation step will compare this spec to the file system and fail fast if any listed item is missing.
   - Expected effect: Ensures all required modules are scaffolded before coding begins, dramatically cuts the number of rounds spent on “file does not exist” failures and aligns the UI flow with actual code structure.
5. **[low] Introduce Sub‑Task Turn Planning to Avoid Turn‑Limit Exhaustion**
   - Evidence: Coder hit its turn limit in rounds 1, 8, 15, 19 (each round lasted >40 min, with round 19 lasting 81 min). The coder was trying to solve many unrelated issues in a single round, leading to stagnation and wasted time.
   - Change: planner prompt: after each major fix (detected via reviewer or validator success), automatically emit a new sub‑task with a fresh turn budget (e.g., 10‑15 turns). Add a pipeline guard that, when the coder approaches its turn limit, pauses the round, records the current state, and starts a new round with the same goal but a fresh turn counter. Also log which files have been modified >3 times and suggest splitting them into separate sub‑tasks.
   - Expected effect: Prevents long, monolithic coder rounds, keeps each iteration focused, and keeps total runtime per round under ~30 min, improving overall throughput and reducing the chance of the run stalling.
